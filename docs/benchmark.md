# 压缩基准：压缩率、画质与缓存

2026-10-27，在 DeepSeek Harness（DSH）`0.2.1-rc.3` 上对本机 266 个附件对象实测，插件为 `@local/dsh-read-image-compress`。插件在 `tools/post-execute` 拦截 `read_image` 的结果，用 Sharp 降分辨率、降码率后替换结果内容。以下数据覆盖这条路径的压缩率、画质损失与缓存行为。

## 结果摘要

- **压缩率**：默认配置 `1568 / 512 KiB` 在 266 张图上把 522.1 MB 压到 57.0 MB，聚合 9.16×，节省 89.1%；相对 DSH 当前 pi-ai 请求层的 87.8 MB 再省 35.1%。
- **编码损失**：默认配置下 242 张被编码的图，PSNR 平均 34.47 dB，SSIM 平均 0.9805（`1-SSIM ≈ 1.95%`）；统一到上限 1280 长边比较时 SSIM 为 0.9862（`1-SSIM ≈ 1.38%`）。文字截图最差一档 SSIM 约 0.968。
- **缓存**：第二次读同一张图 127 ms，第一次 181 ms，约 -30%；第二次新增 0 个对象、0 个 request cache。派生附件在请求层直通，不会额外生成第二个缓存；首次读取会留下一个与派生附件等大的 source variant 缓存。

## 测试方法

### 语料

| 源大小 | 数量 | 源字节 |
|---|---:|---:|
| < 512 KiB | 88 | 24,984,724 |

| 1–2 MiB | 9 | 14,078,216 |

> [!IMPORTANT]
> 语料是“附件库全体”的模拟。插件实际只处理 `read_image` 的结果，用户直接上传的附件不会经过它。全部跑一遍是为了得到稳定的统计量，不代表插件会改写历史附件。

### 编码路径

基准脚本使用与 DSH `dsh-attachment-local` 完全相同的编码参数：

- 解码后执行 `.toColourspace('srgb')`。
- 需要缩放时按长边 resize（`withoutEnlargement`，Sharp 默认 lanczos3）。
- 有 alpha 时输出 **WebP q85, effort 0**；无 alpha 时输出 **JPEG q85**。
- 质量阶梯为 85 → 75 → 60，取第一个不超过 `maxBytes` 的结果；全都不满足时取最小。
- 插件默认值：`maxEdge=1568`、`maxBytes=524288`、`minBytes=131072`、`minResizeScale=0.9`、`downscaleWebp=true`、`skipGif=true`。
- 请求层基线：pi-ai 默认 `requestImagePixelBudget=4,194,304`、`requestImageMaxBytes=1 MiB`；尺寸与字节都不超过目标时直通，否则按同一阶梯重编码。

数据由 DSH 的附件编码路径采集。插件当前默认由 Sharp 直接编码，绝对字节数会略有差别，压缩比与画质趋势不受影响。

### 质量指标

- PSNR 与 SSIM：以原图为参考，按输出尺寸重采样后比较；alpha 图先合成到白底。
- SSIM 用 luma 加 Gaussian window（σ=1.5）的全局均值。
- 另做一张上限 1280 长边的对照表（小于 1280 的图保持原尺寸），避免“缩得越小、在输出分辨率上 SSIM 反而越高”的尺度悖论。
- 指标衡量的是送到模型的那张图的编码与降采样损失，不等价于 OCR 可读性；文字截图需要单独目测。

### 配置权衡

同一批 266 张图，统一到上限 1280 长边比较质量时，三档配置的对比如下：

| 配置 | 输出总字节 | 压缩比 | 节省 | 相对当前请求层 | 1280 长边 PSNR | 1280 长边 SSIM | 1-SSIM |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1280 / 384 KiB | 42.7 MB | **12.23×** | 91.8% | 51.4% | 34.76 dB | 0.9816 | 1.84% |
| **1568 / 512 KiB（默认）** | **57.0 MB** | **9.16×** | 89.1% | 35.1% | **35.47 dB** | **0.9862** | **1.38%** |
| 1920 / 1 MiB | 69.0 MB | 7.56× | 86.8% | 21.4% | 36.89 dB | 0.9901 | 0.99% |

三档都全部命中 q85，没有降到 q75/q60。默认档是体积与质量的折中；模型要读小字时，先试 `1920 / 1 MiB`，而不是继续放大 `maxBytes`（q85 已经是第一档）。

## 画质损失

### 默认配置

242 张编码图按输出分辨率比较：

| 指标 | 平均 | 中位 | p10 | p90 | 最小 | 最大 |
|---|---:|---:|---:|---:|---:|---:|
| PSNR | **34.47 dB** | 34.10 | 32.05 | 36.25 | 30.73 | 46.58 |
| SSIM | **0.9805** | 0.982 | 0.970 | 0.989 | 0.965 | 0.998 |

`1 - SSIM` 平均 1.95%；统一到上限 1280 长边后为 1.38%。

按缩放档位与输出格式分组：

| 分组 | 数量 | PSNR | SSIM |
|---|---:|---:|---:|
| 只重编码、未缩放（scale=1） | 75 | 35.94 dB | 0.9866 |
| 0.75–0.9 缩放 | 135 | 33.47 dB | 0.9782 |
| <0.75 缩放 | 32 | 35.21 dB | 0.9755 |
| 输出 JPEG（不透明） | 62 | 34.15 dB | 0.9745 |
| 输出 WebP（有 alpha） | 180 | 34.58 dB | 0.9825 |

“<0.75 缩放”组的 PSNR 反而高于 0.75–0.9 组，这是尺度悖论：原图缩到更小后，参考图也一起变平滑。该组 SSIM 仍然更低（0.9755），且这些图多为小图或低细节图。判断质量不要只看 PSNR。

### 最差样本

最差的四张编码图：

| 原图 | 输出 | 压缩比 | PSNR | SSIM |
|---|---|---:|---:|---:|
| PNG 380×780（alpha，scale=1） | WebP 380×780 | 6.7× | 30.73 dB | 0.9880 |
| PNG 480×900（alpha，scale=1） | WebP 480×900 | 3.1× | 30.85 dB | 0.9950 |
| PNG 1800×1143（不透明） | JPEG 1568×996 | 9.8× | 31.48 dB | **0.9682** |
| PNG 1920×1143（不透明） | JPEG 1568×933 | 10.0× | 31.63 dB | **0.9694** |

- 低 PSNR 的 alpha 图集中在渐变与平滑区域，SSIM 仍高（0.988–0.995）。
- 不透明 PNG 转 JPEG 的文字截图 SSIM 最低（约 0.968），典型风险是细字边缘振铃；小字可读性需要目测。
- 有 alpha 的图仍走 WebP，不 flatten、不丢透明；这是 DSH 编码器的选择，不是插件额外降质。

## 缓存行为

> [!NOTE]
> 本节的缓存条目由 `readImageRequest()` 的编码路径产生；当前默认的 Sharp 直编码不写 source variant 缓存，只保留进程内 LRU，见 [插件说明](../README.md)。

### 受控用例

生成一张全新的 2000×1500 PNG（4,762,424 bytes）放到临时目录，连续 `read_image` 两次。

第一次读取的结果：

| 项 | 结果 |
|---|---|
| `read_image` 工具耗时（session log `tool/call` → `tool/result`） | **181 ms** |
| 源对象（DSH 规范化后） | 407,502 B JPEG（源 4.76 MB > 4 MiB，附件入库规范化时被重编码） |
| 插件派生附件 | **247,094 B JPEG，1568×1176** |
| attachment objects 增量 | **+2**（源 + 派生） |
| request-images 缓存增量 | **+1**（247,094 B，source variant） |
| 工具信封 | `image/jpeg, 1568x1176, 247094 bytes (downscaled from 2000x1500)` |

第二次读取同一个文件的结果：

| 项 | 结果 |
|---|---|
| 工具耗时 | **127 ms**（-54 ms，约 -30%） |
| attachment objects 增量 | **0** |
| request-images 缓存增量 | **0** |
| 派生附件引用 | 与第一次相同（内容寻址去重） |

### 代价与边界

- 首次读取会留下一个与派生附件等大的 source variant 缓存。图片只读一次时，相当于额外占用约 1× 派生附件的磁盘；读多次时，从第二次起摊销。
- 源图本身小于 4 MiB 时，`read_image` 的 source `saveImage` 会直通，首次读取更快。上面的 181 ms 包含 4.76 MB PNG 超过 4 MiB、DSH 先规范化成 407 KB JPEG 的成本。
- 第二次仍有 127 ms，主要是 `read_image` 工具重新读源文件，`saveImage` 重新做 source 规范化与校验；hook 的 encode 已经命中缓存。再加插件级内存 LRU（按 `attachmentId + config` 缓存派生引用）只能省掉剩余的一小段，收益有限，本次没有实现。
- 修改配置（`maxEdge`、`maxBytes`、`minResizeScale`）会改变 target，从而生成新的 variant；旧缓存不会自动删除。
- 缓存命中不改变正确性：派生附件是内容寻址的，重复读取拿到同一个对象；源图与历史不可变。

## 现场结果

现场结果与基准互相校验：

| 输入 | 插件输出 | 对照 |
|---|---|---|
| 3.97 MB PNG，1800×1143，alpha | WebP 1568×996，287,108 B | 基准预测 287 KB 档 |
| 714 KB PNG，1230×480，不透明 | JPEG 1230×480，104,610 B | 基准预测 ~102 KB 档 |
| 1600×1450 PNG，alpha | WebP **1600×1450**，388,224 B | 与当前请求层 388,224 B 一致；`minResizeScale` 生效 |
| 2000×1500 PNG，缓存测试 | JPEG 1568×1176，247,094 B | 第二次读取 0 新对象 / 0 新缓存 |

## 结论

1. 默认 `1568 / 512 KiB` 是合理的平衡点：存储与 UI 约 9×，模型请求相对当前请求层省 35%，SSIM 0.986（上限 1280 长边）。
2. 文字截图要看 SSIM 最低档（约 0.968）并目测小字。模型要读小字时，把配置切到 `1920 / 1 MiB`：存储仍有 7.6×、请求层省 21%、SSIM 0.990。
3. 不要用更小的 `maxEdge` 去换质量指标：1280 档在输出分辨率上看起来不差，实际分辨率损失更大；用上限 1280 长边的对照表比较才公平。

## 复现方法

- 基准脚本对 `C:\Users\q1325\.dsh\attachments\v1\objects` 全量执行。
- 使用从 DSH `app.asar` 提取的 Sharp 0.35.5 / libvips 8.18.7，编码参数与 `dsh-attachment-local` 一致。
- 质量指标用 Python PIL 加 numpy、scipy（PSNR、Gaussian-window SSIM）。
- 计时来自当前 session 的 `tool/call` / `tool/result` 事件（zstd 日志解压）。
- 机器、缓存状态与源图内容都会影响绝对耗时；压缩比与质量分布可复现，毫秒数只作相对参考。
