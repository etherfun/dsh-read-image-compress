# read-image-compress：压缩率 / 编码损失 / 缓存测试

> 2026-10-27 · DSH `0.2.1-rc.3` · 本机 266 个附件对象 · 插件 `@local/dsh-read-image-compress`
>
> **版本说明：** 本文数据基于 v0.1（DSH attachment encoder，q85/effort0）。v0.2 改用 Sharp 直接编码并加入 `quality` / `resolutionScale` / `format` 设置；同一样本默认 q85/effort4 为 255,086 bytes（v0.1 为 287,108）。压缩率与质量趋势仍适用，精确数值以当前设置重测为准。

## 0. 一句话结论

- **压缩率**：默认配置 `1568 / 512 KiB` 在 266 张图上把 **522.1 MB → 57.0 MB**，聚合 **9.16×**，**节省 89.1%**；相对 DSH 当前 pi-ai 请求层（87.8 MB）再省 **35.1%**。
- **编码损失**：默认配置下 242 张被编码的图，PSNR 平均 **34.47 dB**、SSIM 平均 **0.9805**（`1-SSIM ≈ 1.95%`）；统一到上限 1280 长边比较时 SSIM **0.9862**（`1-SSIM ≈ 1.38%`）。文字截图最差一档 SSIM 约 **0.968**。
- **缓存**：第二次读同一张图 **127 ms**，第一次 **181 ms**（-30%）；第二次 **0 个新对象、0 个新 request cache**。derived attachment 在请求层直通，不会额外生成第二个缓存；首次读取会留下一个与 derived 等大的 source variant 缓存。

| 源大小 | 数量 | 源字节 |
|---|---:|---:|

| 1–2 MiB | 9 | 14,078,216 |

> 这是“附件库全体”的模拟：插件实际只处理 `read_image` 的结果，用户直接上传的附件不会经过它。把它们全部跑一遍，是为了得到稳定的统计量，而不是声称插件会改历史附件。

### 1.2 复刻的编码路径

Benchmark 使用与 DSH `dsh-attachment-local` 完全相同的编码参数：

- 解码后 `.toColourspace('srgb')`；
- 需要缩放时按长边 resize（`withoutEnlargement`，sharp 默认 lanczos3）；
- 有 alpha → **WebP q85, effort 0**；无 alpha → **JPEG q85**；
- 质量阶梯 85 → 75 → 60，取第一个 ≤ `maxBytes` 的；全都不满足取最小；
- 插件默认：`maxEdge=1568`、`maxBytes=524288`、`minBytes=131072`、`minResizeScale=0.9`、`downscaleWebp=true`、`skipGif=true`；
- 请求层基线：pi-ai 默认 `requestImagePixelBudget=4,194,304`、`requestImageMaxBytes=1 MiB`；尺寸和字节都 ≤ target 时直通，否则按同一阶梯重编码。

### 1.3 质量指标

- **PSNR / SSIM**：以原图为参考，按输出尺寸重采样后比较；alpha 图先合成到白底。
- SSIM 用 luma + Gaussian window（σ=1.5）的全局均值。
- 另做一张 **上限 1280 长边** 的对照表（小于 1280 的图保持原尺寸），避免“缩得越小、在输出分辨率上 SSIM 反而越高”的尺度悖论。
- 这些指标衡量的是“送到模型的那张图的编码/降采样损失”，**不等价于 OCR 可读性**；文字截图需要单独目测。

### 2.2 一个被修掉的坏情况：边际缩放

第一版只判断 `longEdge > maxEdge`，于是 1600×1450 会被缩到 1568×1421。实测这类 **0.98× 的边际缩放反而让 WebP 变大**：

| 图片 | 当前请求层 | 第一版输出 | 修后输出 |
|---|---:|---:|---:|
| 1600×1450 PNG | 388,224 B | **469,798 B** @1568×1421 | **388,224 B** @1600×1450 |
| 1600×900 PNG | 190,456 B | **207,646 B** @1568×882 | **190,456 B** @1600×900 |

第一版在 242 张中有 **10 张** 的输出大于当前请求层，最多 +21%。加入 `minResizeScale=0.9`（只有 `maxEdge` 不超过长边 90% 才缩放）后，这 10 张全部消失；live 验证 1600×1450 已输出 1600×1450 / 388,224 B，和当前请求层一致。

### 2.3 配置权衡（同一 266 张图，上限 1280 长边比较质量）

| 配置 | 输出总字节 | 压缩比 | 节省 | 相对当前请求层 | 1280 长边 PSNR | 1280 长边 SSIM | 1-SSIM |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1280 / 384 KiB | 42.7 MB | **12.23×** | 91.8% | 51.4% | 34.76 dB | 0.9816 | 1.84% |
| **1568 / 512 KiB（默认）** | **57.0 MB** | **9.16×** | 89.1% | 35.1% | **35.47 dB** | **0.9862** | **1.38%** |
| 1920 / 1 MiB | 69.0 MB | 7.56× | 86.8% | 21.4% | 36.89 dB | 0.9901 | 0.99% |

三档都全部命中 q85，没有降到 q75/q60。默认档是“体积/质量”的折中；如果模型要读小字，建议先试 1920/1 MiB，而不是继续放大 `maxBytes`（q85 已经是第一档）。

### 3.1 默认配置（1568 / 512 KiB）

242 张编码图，按输出分辨率比较：

| 指标 | 平均 | 中位 | p10 | p90 | 最小 | 最大 |
|---|---:|---:|---:|---:|---:|---:|
| PSNR | **34.47 dB** | 34.10 | 32.05 | 36.25 | 30.73 | 46.58 |
| SSIM | **0.9805** | 0.982 | 0.970 | 0.989 | 0.965 | 0.998 |

`1 - SSIM` 平均 **1.95%**；统一到上限 1280 长边后 **1.38%**。

分组：

| 分组 | 数量 | PSNR | SSIM |
|---|---:|---:|---:|
| 只重编码、未缩放（scale=1） | 75 | 35.94 dB | 0.9866 |
| 0.75–0.9 缩放 | 135 | 33.47 dB | 0.9782 |
| <0.75 缩放 | 32 | 35.21 dB | 0.9755 |
| 输出 JPEG（不透明） | 62 | 34.15 dB | 0.9745 |
| 输出 WebP（有 alpha） | 180 | 34.58 dB | 0.9825 |

> “<0.75 缩放”PSNR 反而比 0.75–0.9 高，是尺度悖论：原图被缩到更小后，参考图也一起变平滑；SSIM 仍然更低（0.9755），且这些图本来多为小图/低细节图。看质量不要只看 PSNR。

### 3.2 最差的几张

| 原图 | 输出 | 压缩比 | PSNR | SSIM |
|---|---|---:|---:|---:|
| PNG 380×780（alpha，scale=1） | WebP 380×780 | 6.7× | 30.73 dB | 0.9880 |
| PNG 480×900（alpha，scale=1） | WebP 480×900 | 3.1× | 30.85 dB | 0.9950 |
| PNG 1800×1143（不透明） | JPEG 1568×996 | 9.8× | 31.48 dB | **0.9682** |

- 低 PSNR 的 alpha 图主要是渐变/平滑区域，SSIM 仍高（0.988–0.995）。

- 有 alpha 的图仍走 WebP，不 flatten、不丢透明；这是 DSH 编码器的选择，不是插件额外降质。

## 4. 后期缓存测试

> v0.2 默认走 Sharp 直编码，不经过 `readImageRequest()`，因此不会产生这里的 source variant 缓存；下面的数据是 v0.1 / Sharp 不可用时的回退路径。v0.2 的进程内 LRU 另见 README。

### 4.1 受控用例

生成一张全新的 2000×1500 PNG（4,762,424 bytes）放到临时目录，连续 `read_image` 两次。

**第一次读取：**

| 项 | 结果 |
|---|---|
| `read_image` 工具耗时（session log tool/call → tool/result） | **181 ms** |
| 源对象（DSH 规范化后） | 407,502 B JPEG（源 4.76 MB > 4 MiB，入库被重编码） |
| 插件 derived 对象 | **247,094 B JPEG，1568×1176** |
| attachment objects 增量 | **+2**（源 + derived） |
| request-images 缓存增量 | **+1**（247,094 B，source variant） |
| 工具信封 | `image/jpeg, 1568x1176, 247094 bytes (downscaled from 2000x1500)` |

**第二次读取同一文件：**

| 项 | 结果 |
|---|---|
| 工具耗时 | **127 ms**（-54 ms，约 -30%） |
| attachment objects 增量 | **0** |
| request-images 缓存增量 | **0** |
| derived 引用 | 与第一次相同（内容寻址去重） |

### 4.2 缓存到底命中了什么

1. 插件的 `ctx.attachments.readImageRequest(source, target)` 会把 source→target 的编码结果写到：
   `C:\Users\q1325\.dsh\cache\attachments\request-images\<xx>\<sha256>`
   第一次 +1；第二次同一 target 直接读这个文件，不再 encode。
2. 插件随后 `saveImage(derived bytes)` 是内容寻址的；第二次得到同一个 `attachmentId`，不会新增对象。
3. **derived attachment 本身不会生成第二个 request cache**：它 ≤1 MiB、长边 1568，provider 的 4 MP / 1 MiB 目标会直接直通。所以第一次缓存增量是 +1（source variant），不是 +2。
4. 该缓存是全局的（`~/.dsh/cache/attachments/request-images`），跨 session 保留；本次测试前 162 个文件 / 48,887,055 B，第一次后 163 个 / 49,134,149 B，第二次后不变。

### 4.3 缓存的代价与边界

- **首次读取会留下一个与 derived 等大的 source variant 缓存**。如果一张图只读一次，这相当于额外的 ~1× derived 磁盘；如果读多次，第二次起摊销。
- 如果源图本身 <4 MiB，`read_image` 的 source `saveImage` 会直通，首次读取会更快；上面的 181 ms 包含“4.76 MB PNG >4 MiB → DSH 先规范化成 407 KB JPEG”的成本。
- 第二次仍有 127 ms，主要是 `read_image` 工具体重新读源文件、`saveImage` 重新做 source 规范化与校验；hook 的 encode 已经命中缓存。再加插件级内存 LRU（按 `attachmentId + config` 缓存 derived ref）只能省掉剩余的一小段，收益有限，本次没有实现。
- 改配置（`maxEdge` / `maxBytes` / `minResizeScale`）会改变 target，从而生成新的 variant；旧缓存不会自动删除。
- 缓存命中不改变正确性：derived 是内容寻址的，重复读取拿到同一个对象；源图/历史不可变。

## 6. 结论与建议

1. **默认 1568 / 512 KiB 是一个合理的平衡点**：存储/UI 约 9×、模型请求约 1.54×（相对当前 87.8 MB 省 35%），SSIM 0.986（上限 1280 长边）。
2. **文字截图优先看 SSIM 最低档（~0.968）和目测小字**；如果模型要读小字，把配置切到 1920 / 1 MiB，存储仍有 7.6×、请求层省 21%，SSIM 0.990。
3. **不要用“更小的 maxEdge”来换质量指标**：1280 档的 PSNR/SSIM 在输出分辨率上看起来不差，但实际分辨率损失更大；用上限 1280 长边表比较才公平。
4. **缓存是有效的，但不是“免费”的**：第二次读取 -30%；首次会多一个 derived 大小的 request cache。图片读一次为主时，这是可接受的成本；如果磁盘紧张，可考虑后续用 sharp 自编码绕过 request cache（会引入依赖），或定期清理 `~/.dsh/cache/attachments/request-images`。
5. **本次修复的边际缩放问题**（`minResizeScale=0.9`）应保留：没有它，10/242 张图的发送字节会比当前 DSH 还大，最多 +21%。

## v0.3 变更说明（2026-10-28）

v0.3 只改「结果呈现」与「结果内容装配」，编码器、质量阶梯、缓存全部沿用 v0.2：

- 压缩后图片不再带 `originalDimensions`，内置大小行显示为 `1568×980 · 44.0 KB`；
- 展开底部新增一行：`原图: 3200×2000 · 2.05 MB · PNG | 压缩后: 1568×980 · 43.9 KB · JPEG | 压缩比: 47.9×（体积 ↓97.9%，长边 49%）`；
- 因此上表的体积/画质数据仍然有效，只有「原图字节」现在取磁盘真实大小（`stat` 结果），规范化过的源不会再被误当成原图。

## v0.15 变更说明（2026-10-29）：两种模式的实测

v0.15 把管线拆成「分辨率」「码率」两个独立开关，编码器与质量阶梯本身没变。用真实 sharp（libvips 8.18.7，与运行中的 DSH 同一份构建）在**同一张** 3200×2000 源上跑四个组合：

| 组合 | 输出 | 字节 | 备注 |
|---|---|---:|---|
| 分辨率 + 码率 | 1568×980 JPEG | 65,727 | 源 12.2 MB PNG（高频噪声很重），189.5× |
| 仅分辨率 | 1568×980 PNG | 2,122,127 | 无损，与直接 resize 逐像素一致 |
| 仅码率 | 3200×2000 JPEG | 442,923 | 像素未动，q85 首档即落入 512 KiB |
| 都关闭 | — | — | 不做任何替换 |

保真档（仅分辨率）在已压缩源上的表现：

| 源 | 输出 | 停留档位 |
|---|---|---|
| 7,930,220 B JPEG q100 4:4:4 | 1568×980 JPEG 1,289,322 B | 100 级，4:4:4 色度生效 |
| 539,480 B JPEG q78 | 1568×980 JPEG 133,225 B | 90 级，仍高于源质量 |

结论：仅分辨率档的字节上限取「源文件字节数」，所以结果**永远不会比原图大**；停在 90 级时反而比源 q78 更清晰。默认组合（两个都开）的压缩率与画质结论不受影响。
